# Portfolio Agent Instructions

You are working on a portfolio website for a design-minded full-stack software engineer and product builder.

Before making any visual, UX, frontend or interaction decision, read:

`DESIGN_SYSTEM.md`

Treat that document as the source of truth.

Do not reinterpret the visual direction unless explicitly instructed.

## Core objective

Build a portfolio that itself demonstrates:

- excellent frontend engineering
- visual design ability
- interaction design
- systems thinking
- technical depth
- attention to detail

The visual benchmark is the level of polish found on products such as Raycast.

The website must feel original and must not copy another website.

## Working principles

For every feature or component:

1. understand its purpose
2. determine its information hierarchy
3. choose the simplest layout that communicates it clearly
4. apply the established design system
5. add interaction only if it improves the experience
6. verify responsive behavior
7. verify keyboard accessibility
8. verify performance impact
9. compare the result against the quality bar in `DESIGN_SYSTEM.md`

Do not introduce a new design pattern if an existing system pattern can solve the same problem.

## Visual discipline

Avoid generic AI-generated website patterns.

Do not default to:

- large rounded cards
- excessive gradients
- centered hero layouts
- pill-shaped everything
- huge icons
- generic glassmorphism
- repetitive card grids
- random floating decorative elements
- generic dark SaaS aesthetics

Prefer:

- strong typography
- intentional whitespace
- asymmetric but structured composition
- thin borders
- layered technical visuals
- custom diagrams
- subtle texture
- high-quality micro-interactions
- meaningful technical UI elements

## Interaction

Standard navigation and interaction must always work.

Advanced interactions such as:

- command palette
- Vim navigation
- CLI commands
- keyboard shortcuts
- easter eggs

are progressive enhancements.

Never require the visitor to discover them to access important information.

## Gamification

Gamification should reward curiosity rather than distract from information.

It should feel like exploring a software system.

Use:

- discoverable commands
- shortcuts
- hidden states
- technical interactions
- contextual easter eggs

Do not use fake game mechanics such as XP or achievements.

## Implementation quality

Do not only make the site look correct.

Ensure the implementation is:

- maintainable
- componentized appropriately
- semantically structured
- accessible
- responsive
- performant
- consistent

Avoid unnecessary abstraction.

Avoid unnecessary dependencies.

Prefer native platform capabilities when suitable.

## When uncertain

If a design decision is ambiguous, choose the option that is:

1. clearer
2. more restrained
3. more technically coherent
4. more consistent with the existing system

Do not add decoration merely to make a section look more visually interesting.

Instead improve:

- composition
- hierarchy
- typography
- spacing
- interaction
- visualization

## Reference philosophy

Use these references for principles, not copying:

- Raycast: overall polish, hero quality, depth, hierarchy, textures
- Resend: custom visualizations, diagrams, UI elements, interactive objects
- Linear: restraint and information hierarchy
- Vercel: clarity and grid discipline
- Actual Source: interface reflecting the creator's domain

Do not reproduce exact layouts, components or visual assets from these sites.

## Final review

Before considering work complete, review the page at:

- desktop large
- laptop
- tablet
- mobile

Check:

- typography
- spacing
- visual hierarchy
- interaction states
- keyboard controls
- focus states
- reduced-motion behavior
- loading behavior
- performance
- visual consistency

The result should look intentionally designed, not AI-generated.
